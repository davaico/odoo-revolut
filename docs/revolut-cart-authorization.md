## Selected authority model

Use the native persisted `pos.order` draft for retail and Restaurant, augmented by a server-only authorization record and tender versions. Compare alternatives:

| Option | Decision |
| --- | --- |
| Save native draft and trust `amount_total` | Reject: writable browser financial inputs and arithmetic alone do not establish permission. |
| Sign existing browser snapshot/total | Reject: a signature authenticates unchecked inputs and does not reserve remaining funds. |
| Validated quote/version without a draft | Viable only with the same validation and ledger; duplicates native persistence/recovery/checkout. Not selected. |
| Validated persisted draft plus immutable authorization/version | Selected: native cart/recovery, bounded permitted edits, server calculation and a shared allocation boundary. |

**Guarantee:** a requested base charge belongs to one validated cart and consumes only its remaining authorized base allocation; any additional customer tip requires separate authenticated provider evidence. Native unrestricted cashiers may choose manual prices; authorizing those edits does not attest the physical basket, customer tip consent or cash actually received. The policy does not fix general POS HR employee authentication. The authenticated Odoo user is the server actor; browser employee/role/context fields supply attribution only. Existing company/session access checks remain mandatory; ticket 30 investigates shared-register permission separately.

### Validate and calculate before authority exists

1. Resolve exact persisted order ID **and** UUID, company, originating session/config and currency; require an open session, draft sale, readable/writable order and configured tender. Reject ambiguous duplicate identity or a Restaurant table alias to another UUID. A positive charge never authorizes a return; existing refund allocation remains separate.
2. Preflight bounded input with ticket 24's limits before numeric expansion, iteration or costly tax work. Accept editing commands and selected products/quantities, not submitted financial results. Validate product existence/POS eligibility (the configured tip product is an explicit exception), company, UoM precision, allowed pricelist, selected attributes/combo relationships and allowed fiscal position/preset. Retain legitimate negative/discount lines in a sale where native controls allow them; total and positive charge must remain valid. Return-linked lines go through the existing return boundary.
3. Server-derive company product taxes and fiscal mapping, tax-included conversion, valid variant/attribute extras and automatic pricelist prices. Do not trust submitted tax IDs, `price_extra`, `price_type`, subtotals, total, currency rate or amount-paid. Prices use the server authorization time and native Product Price precision; if the browser differs, return the canonical cart for review before dispatch, never silently charge a new amount.
4. Treat an explicit editable price as an authorized command when native Price Control is off. With restriction on, any deviation from the native computed default requires authenticated POS manager approval of the exact cart version and override values. Merely changing `price_type` to `original` cannot bypass this. Preserve manual discounts 0–100 when enabled by configuration; automatic pricelist/combo discounts must be server-derived. A minimal HR employee's UI restriction is not server proof of a distinct principal.
5. Reuse native Python pricelist and account-tax helpers. Quantity tiers, included/excluded taxes, company rounding, fiscal mapping, preset/customer defaults, variants, tracked-product aggregation and combos need pinned frontend/backend parity fixtures. Do not replace all prices with list price. No matching Python combo allocator was found: a narrow parity implementation may be required. If the complete native slice cannot fit ticket 27, provide a concrete prerequisite breakdown before landing a partial guard; do not silently disable normal cart features or accept unchecked automatic prices.
6. Recompute line subtotals and whole-order tax/total with `account.tax`/`pos.order._compute_prices` **after** authorizing inputs. Normalize currency amounts to minor units using existing helpers. Store canonical financial contents and their provenance (automatic pricing inputs or approved manual edit), derived taxes/totals, pricing time, tip mode/approval, rounding configuration and owner identity as immutable authorization data.

The server-owned authorization model has no POS-user create/write/unlink ACL. Public preparation/approval methods recheck access and allow only these actions; internal bypass scopes follow the existing cursor-bound Python pattern, not a forgeable context flag. Draft `create/write/unlink`, line changes, payment commands, `sync_from_ui`, direct ORM and settlement all acquire the shared order boundary for relevant financial mutations. Unvalidated native drafts can exist but cannot dispatch. Any relevant mutation invalidates unexposed authority; ordinary writes cannot create/alter approval or preserve an old version.

### Approval and online preparation protocol

Proposed public seam names may follow existing repository naming during implementation:

- POS completes native draft synchronization and obtains the exact canonical record. Awaiting `syncAllOrders` alone is insufficient: it can skip or return a connection failure. Preparation verifies the committed draft in a fresh owned transaction. Offline preparation/dispatch fails without a financial POST.
- `pos.order.revolut_prepare_payment(order_id, uuid, expected_cart_version, tender_plan, explicit_tip_action)` performs validation/recomputation under the shared lock, stores authorization and returns canonical version, amount, tip, tender revision and remaining allocation. It never dispatches. Initial prepare may create version 1; retries with the same canonical version are idempotent. Stale writes return current canonical state rather than silently winning.
- A restricted price or large tip returns `approval_required` and the pending canonical version/values. An authenticated POS manager opens that persisted order in their own Odoo session and invokes `revolut_approve_cart` for that exact version and edits. The server checks `group_pos_manager`; cashier browser need not collect or receive manager credentials. Approval is persisted with approver/time and cannot transfer to another cart, price or tip. Then cashier preparation resumes. No employee ID, PIN hash, browser confirmation or supplied approval object suffices.
- `pos.payment.method.revolut_start_payment` requires authorization ID, cart version and tender revision in addition to the existing logical line/retry identity. Authorization ID is a lookup, not a bearer capability. Fresh permission/ownership checks and the reservation precede every financial POST. Supplied amount must equal the named approved slot and fit remaining capacity; neither old amount+snapshot RPC nor client-set record fields can mint authority.
- Preparation is valid for five minutes **only while unexposed**. Before first reservation, revalidate current configuration/pricing permissions and calculation basis; a changed catalog/permission basis requires review/reprepare. After exposure, retain the frozen approved financial basis; catalog changes cannot reprice an already approved charge. A version change or finalization revokes unused eligibility. Expiry never changes an operation or releases funds.

## Explicit tips

The owner clarified that customer selection on the Revolut terminal is the required tipping flow. It happens before card payment but after the POS reserves/dispatches the base allocation. It must not be replaced by mandatory Odoo tip entry or confused with post-capture Restaurant adjustment. See the required terminal-tip contract below. The following rules apply to any Odoo-entered tip compatibility lane, not to customer selection on the terminal.

- Use the native configured tip product through a distinct explicit tip action, with one canonical line, quantity 1, nonnegative amount, no discount and server-derived product taxes. A zero tip means no tip allocation. Reject duplicate/ordinary-product substitutions, forged `tip_amount` metadata or generic price-edit routes that mutate the tip without authorization.
- Tip is included in the server-calculated order total **once**. Native `is_tipped`/`tip_amount` are normalized metadata consistent with the tip line's excluded amount. Do not add `tip_amount` to total or use payment overage to infer/create a tip.
- For the permission threshold, compute non-tip tax-inclusive total `B` using the native tax engine without the tip and before cash rounding. Compute actual tip contribution `K` as whole-cart tax-inclusive total minus `B`, also before cash rounding. An ordinary POS user may approve `0 <= K_minor <= floor(B_minor / 4)` with `B_minor > 0`. A larger tip (or positive tip on zero non-tip balance) requires authenticated POS manager approval of the exact tip/version. This inclusive convention is the implementation choice for the owner's 25% policy and avoids an unchecked taxed tip exceeding the limit. Expose inclusive amount in confirmation; native input price remains subject to its tax treatment.
- Odoo tip entry is allowed before first reservation. Once any attempt is in-flight, uncertain or verified, neither new Odoo-entered tip nor changed base financial cart is allowed, including after a partial capture. Fully retry-safe failed attempts with no verified allocation permit edit and reauthorization; the old attempts remain immutable.
- Disable native Add Tip/setTip before mutation on exposed Revolut orders, including direct ORM, Restaurant TipScreen, bulk Settle and first-cash-line mixed-tender routing. With `set_tip_after_payment` enabled, block new Revolut dispatch with actionable configuration guidance to use the supported terminal tip flow during payment; leave non-Revolut flows native. Do not quietly enable an incompatible workflow or invent terminal adjustment support.
- After capture, preserve the original base cart and charge; only an idempotent provider-proven terminal-tip projection may augment the native order as specified below. A later voluntary tip requires a separately approved future collection workflow. This ticket does not auto-refund, enlarge a capture or alter an existing payment.

## Atomic amount allocation

The **updated `(company_id, order_uuid)` lock row**, shared by preparation, approvals, draft/payment mutations, reservations, observation updates, retries and final settlement, is the serialization boundary. Keep existing per-terminal exclusion. Lock order first, then authorization/tender rows, then operation rows in ascending ID. Existing observation/manager paths that currently lock an operation first must be adapted consistently. Under repeatable-read, serialization/uniqueness conflict restarts the entire admission in a fresh owned cursor; re-reading in a stale cursor is insufficient.

The operation is its reservation: add immutable authorization/cart/tender/slot references to the existing operation rather than a second independent payment state machine. Store approved cash/manual tender slots in the authorization ledger with logical UUID and revision; cashier-entered accepted cash is accounting intent, not independent receipt evidence. Other electronic tenders may conservatively reserve their approved slot but cannot be labeled verified from browser `done`; settlement retains each provider's native verification requirements. Slot identity is unique within the canonical order, and all methods share the ledger; changing method/terminal/line UUID cannot create a second entitlement.

Use currency minor units for bounds. For the frozen base allocation, let `T` be the canonical tax-inclusive base-cart total, including any pre-authorized Odoo tip once, before **cash** rounding. Customer terminal tips occupy the separate ledger described below and cannot enlarge base entitlement. Let `N` be the total server-approved noncash slots in the current tender plan (including proposed Revolut slots), `C` the admitted net cash (cash received minus legitimate cash change), `M` other admitted/reserved non-Revolut slots, `V` all distinct verified Revolut **base** amounts and `U` all non-retry-safe unverified Revolut **base** reservations. Terminal-tip amounts never consume/pay another base allocation; the gross charge is recorded separately. An unsettled verified operation and its linked payment are one contribution, never two; safe predecessor/replacement attempts do not multiply one logical slot.

- Without cash rounding, payable target `P = T`.
- With global rounding, `P = round_cash(T)` using native quantum/method followed by currency rounding.
- With cash-only rounding and a positive cash residual, `P = N + round_cash(T - N)`; require `0 <= N <= T`. With no cash allocation, `P = T`. Derive this from the server-admitted plan, not live unvalidated draft payment lines. The one rounding adjustment belongs to cash, never to a tip or to extra noncash capacity.
- A proposed amount `A` must be positive, equal its authorized slot, satisfy `C + M + V + U + A <= P`, and fit all per-slot and noncash bounds. In cash-only mode additionally cap total noncash plans/reservations at `T`, even when rounding increases `P`. Global rounding can legitimately change the whole order's target, including full card payment; this is separately identified approved rounding, not arbitrary overage.
- Do not count unstarted sibling Revolut plan slots again in `U`: the plan bounds them, and each becomes a reservation on start. Do count admitted non-Revolut tentative slots in `M` conservatively. No tender plan may authorize more than `P`. Replanning tenders under the same lock changes tender revision, not frozen cart version; it may reduce/remove unused slots or admit remaining allocations, but cannot reduce/remove/reassign `V`/`U` or consume them twice. Reject stale tender revisions. Once the admitted contributions fully cover the current rounded payable target, adding a noncash plan cannot reopen the balance or increase that target. A legitimate actual cash correction/reduction must first change the ledger under the same lock; merely declaring another card slot is not a correction. Cash removal can increase card capacity only within the same locked ledger and rounding calculation; no native direct payment write may bypass it.
- A fully verified slot is consumed permanently for this sale even after operation blocking keys clear. Refunds do not replenish the charge entitlement; refund operations keep their original-sale allocation and separate ledger. Terminal/order exclusivity alone is insufficient because sequential verified charges can still overcharge.

Commit reservation and operation together **before** terminal discovery/financial dispatch. Keep dispatch claims durable before each financial POST as now. Competing distinct line UUIDs re-evaluate current capacity, even on different terminals. Duplicate logical starts return the existing operation after identity checks and never reserve/POST twice. Retry replacement requires authoritative `retry_safe`, valid remaining authority and a unique successor. A declined/failed/cancelled label alone does not release capacity; reuse the existing no-charge proof rules. Untouched pre-dispatch rejection returns `dispatched: false` only after locked discovery proves there is no existing financial attempt; an existing uncertain operation returns recovery, never a clean-line rejection.

## Cart versions and lifecycle

Cart version covers exact canonical order identity, line UUIDs/products/quantities/authorized prices/discounts/taxes and financial attribute/combo inputs, pricelist/fiscal position, customer/preset when financially relevant, explicit tip and rounding basis. Normalize/sort as existing bounded snapshots do, but generate the authority from validated server state. Tender revision covers approved allocation identities/amounts and net cash/change. Nonfinancial notes and table-only movement do not alter the financial version. A table move must still validate table ownership/config and cannot switch Dine In/Takeout or merge another order.

| State / trigger | Financial edits, reservation and UI behavior |
| --- | --- |
| Native unsynchronized/unvalidated draft | Ordinary native edits; no Revolut POST. Persist and prepare online. |
| Prepared, unexposed version | Native edits allowed under lock; revoke authority and prepare a new version. Revalidate expired/config-stale authority before reserving. |
| Approval required | Preserve editable cart and pending version; authenticate manager approval separately. No financial POST. A changed version invalidates approval. |
| Reservation committed / created / order creation or intent dispatch | Freeze financial cart and approved slot. Resume committed operation; dispatch claims prevent replay. |
| Pending, local timeout, disconnected browser, malformed evidence or missing IDs | Keep reservation and original ownership. Show Check status/reconciliation. Expiry, cancellation request, empty payment list and browser removal do not prove no charge. |
| Terminal completed intent without verified underlying payment | Remain reserved/unpaid; continue verification. Captured gross payment without proven tip breakdown remains financially exposed and awaiting tip evidence. |
| Verified partial payment | Convert reserved contribution to verified consumed contribution under the same lock. Keep financial cart/tip frozen; admit only remaining tender slots. Never complete partial order automatically. |
| Safe failure/cancel/decline with authoritative retry safety | Release only that attempt's reservation under lock; retain history. If no verified/uncertain contributions remain, cart edit/reprepare permitted. Retry uses unique successor. |
| Untouched rejection: missing/stale authority, oversized amount, busy terminal | No operation/financial POST for that untouched request. Correct/prepare/remove line with actionable UI; locked discovery wins if an older attempt exists. |
| Verified full settlement | Under same boundary, bind exact frozen base order/version, every verified Revolut base slot/gross reference, any proven terminal-tip projections, net non-Revolut allocations and native rounding target. Native order completion follows only full verified settlement. Mark authority consumed; no further charge. |
| Reload, lost prepare/start response, second eligible cashier | Fetch exact original server order/version/ledger and existing operations first. Restore payment lines by logical UUID. Browser serialization cannot change ownership or redispatch unknown operations. Server read access remains checked. |
| Restaurant shared register, transfer, split/merge | Recover exact original ownership even if native browser loading substitutes current config/session. Same-order table-only move allowed. Split/merge/reassignment of exposed financial contents rejected on server and UI. Unexposed operations can be reauthorized after a normal split. |
| Session closing/closed | New reservations require original session open. Normal and direct administrative closure paths must reject uncertain/in-flight or verified-but-unsettled allocations, including operations lacking a native draft. Use exact original session for recovery; never native automatic reassignment. |
| Historical paid/verified legacy operation | Preserve original immutable references/receipts/refund allocation. Do not fabricate historical authorization or re-send payment. Missing authorization must be visibly legacy, not proof of a new remaining balance. |
| Historical unresolved legacy operation / already closed session | Reconcile through existing manager flow using original identity; no new reservation/replay. Associate a provable original cart and financial evidence only via audited manager action. If evidence cannot establish safe continuation, keep blocked; no total invented from amount charged. |

Legacy safe failed history permits preparation only after existing no-charge proof; legacy verified or uncertain history prevents new dispatch until an audited compatibility decision establishes the original entitlement. This is not an automatic amount-based backfill. If safe original-session settlement of a historical orphan cannot be established, retain manager reconciliation and explicit manual accounting handoff rather than automatically transferring it to a new session. Existing full/partial refunds remain linked to their original verified transaction.

## Required terminal-selected tip contract

The owner's final scope decision is: **terminal tips are required; they were the original intended tipping flow.** This supersedes the initial Odoo-entry-only assumption. The terminal asks the customer before presenting the card/payment screen, but the POS has already dispatched the base request.
