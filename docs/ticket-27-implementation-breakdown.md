## Concrete package scope

P1 uses the existing bounded snapshot limits before numeric expansion or expensive work, but calculates authority from permitted persisted inputs. Resolve ID and UUID together with original company/session/config/currency and draft-sale access. Validate eligible products, UoM precision, permitted pricelists, partner/preset/fiscal mapping, attributes and combo relationships. Derive taxes, variant/no-variant extras and automatic prices at the server pricing time using native helpers. Include quantity/date/UoM tiers, tracked-product aggregation, fixed/percentage/formula/nested pricelists, combo allocation and included/excluded/global/per-line tax rounding fixtures. Preserve legitimate negative/discount lines, enabled manual discounts and unrestricted cashier prices. Restricted deviations require the exact manager approval implemented by P2; browser `price_type`, employee/PIN/role and approval objects are never proof. Provide canonical provenance and preflight representability of tax-inclusive terminal tips with native Product Price precision. Reject unsupported configuration before dispatch.

P2 adds no POS-user create/write/unlink ACL for authority records. Preparation, exact-version authenticated manager approval and tender replanning are checked public methods. Five-minute expiry applies only while unexposed; configuration/pricing permissions are revalidated before the first reservation. Lock order is updated order row, authority/tender rows, then operation rows by ID everywhere, including existing observation/manager paths. Order/line/payment create/write/unlink, `sync_from_ui`, approvals, cash changes, reservation and finalization share this boundary. Relevant unexposed edits invalidate authority; exposed financial edits fail. Net cash/change, other electronic reservations, verified base amounts and unsafe in-flight base reservations consume each contribution once. Use the contract's no-rounding/global/cash-only payable formulas; tips and refunds never replenish base entitlement. Preserve terminal exclusion, durable dispatch claims and unique retry successors. Unknown outcomes never release capacity through expiry, browser deletion, empty payment lists or a failure label alone.

P3 adds authenticated `POST /api/report-runs`, fixed-path run polling/file retrieval and bounded CSV parsing independently of the existing dictionary-JSON adapter. Report creation is a non-payment mutation, distinct from financial order/intent/refund POST counters. Persist original report/payment identities and creation-time window; limit columns, bytes, rows and decimal text. Do not request cardholder columns or follow report URLs. Require exactly one matching payment/order/currency/location, successful final capture, explicit numeric zero or nonnegative tip, exact major-to-minor conversion and gross cross-check; reject wrong/duplicate/conflicting rows, refunds, ambiguous units and unexplained surcharge. Inspect the pushed order payment list for an unexpected second successful payment. Persist immutable verified gross/tip/provenance separately from requested base. Missing/expired/late evidence retains exposure and resumes report retrieval without financial replay. A report file expiring after 24 hours does not release a reservation.

P4 completes native online persistence and exact original order recovery before preparation; merely awaiting `syncAllOrders` does not establish a committed draft. Restore slot UUIDs, authority/cart/tender/projection revisions and original ownership on reload/shared-register recovery. Add actionable canonical review and manager approval UI without collecting manager credentials in the cashier browser. An untouched rejection permits correction/removal only after locked discovery proves absence of an existing attempt; existing uncertainty remains status/reconciliation-only. Captured evidence alone may display “Payment received — awaiting terminal tip details”; it cannot complete the sale. Keep bounded POS waiting and background/manager reconciliation. Project proven per-payment tips once to one canonical tip line or deterministic aggregate, with exact native inverse tax calculation and gross tender updates in a cursor-bound server-only evidence scope. Base stays frozen. Global-rounded base `10.00` plus paid tip `0.03` settles and prints `10.03`, without re-rounding to `10.05`. Partial verified payments admit only remaining base slots and do not complete the order. Guard Restaurant cash-first mixed-tender tip routes, direct ORM tips, exposed split/merge/reassignment and shared-session rewriting; permit valid table-only movement. Reject fresh Revolut dispatch under `set_tip_after_payment` with supported configuration guidance. Normal and administrative session closure must include orphan/exposed operations and verified-but-unsettled allocations.

P5 retains original transaction references and requested amounts, using verified gross only where evidence exists. Payment/refund receipts display gross and base/tip decomposition without rewriting earlier documents. Full refund includes the captured tip; partial refund requires explicit original base/tip allocation. Maintain independent reserved/verified ceilings for both components under locks, alongside existing return-line/tender bounds and idempotent refund dispatch. Prove tip-product return semantics, mixed/card allocations, taxed tips and provider original-order gross/refunded amount checks. Update refund selection and gross receipt/tender validation together. No amount-difference inference or automatic refund of past overcharges. Legacy paid/verified operations retain receipts and existing full/partial refunds; unexposed drafts and provably safe failed history can prepare normally. Historical uncertain/verified exposure cannot gain new authority through fabricated backfill or automatic replay. Audited manager association must establish original cart/entitlement or retain explicit reconciliation/manual accounting handoff, especially for closed-session orphans. Upgrade itself makes no Merchant call and modifies no historical provider reference.

P6 exercises the entire approved contract matrix on a fixed combined revision. Retain required terminal selection; reject an existing Odoo-tip cart in terminal mode before exposure to avoid dual prompting. Do not invent a provider suppression flag or apply the cashier 25% cap to customer terminal tips. If a separate Odoo compatibility lane is later confirmed, its explicit canonical tip is included once and its tax-inclusive 25%/authenticated-manager policy remains as approved. Non-Revolut native tipping stays supported.
