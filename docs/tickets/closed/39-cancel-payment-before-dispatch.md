## Triage findings

Mission audit finding D1 was reproduced at `01718690f355081c635c959d99d1a4e65a61e75e`. The relevant production state-machine and adapter code is unchanged at the triage checkout `34b59ef8cb810089e56def38f5b03a6b5aaec50d`. This is a cancellation correctness gap, not an authorization to refactor the payment architecture.

The payment preparation adapter performs several asynchronous operations: saving the native draft, obtaining server cart authorization, and refreshing canonical data. `RevolutPaymentState.cancel` notices cancellation during discovery/preparation, sets `owner.cancelDiscovery`, and waits for the request to finish. `waitForResult` checks that flag after initial discovery and after refund preparation, but not after payment preparation. It therefore dispatches the payment even though cancellation arrived first.

Once dispatch returns, the request waits for `owner.cancellation`; that cancellation is itself waiting for the request. The foreground timeout eventually breaks the dependency and sends provider cancellation, approximately 60 seconds after the start of the request. During that interval the customer may complete the unwanted payment. The reproduction does not establish duplicate charging or a final-verification bypass.

### Reproduction and evidence

Use the existing state-machine fixture with a deferred `preparePayment` and controlled clock:

1. Start a fresh payment. Let initial `revolut_find_payment` return no attempt; leave preparation unresolved.
2. Call cancellation while preparation is pending.
3. Resolve preparation with a valid prepared authorization. Let a mocked start return a pending operation.
4. Observe that start is called despite cancellation. Advance the clock beyond the foreground deadline; observe that only then is provider cancellation called.

Observed production-module call sequence:

```text
Before advancing time: revolut_find_payment, revolut_start_payment
After timeout: revolut_find_payment, revolut_start_payment,
```

### Proposed fix direction

Honor the pending cancellation after payment preparation and before financial start. Finish the request without creating a dependency on its own cancellation promise. Preserve a prior safely failed operation when this happens during preparation of an explicit retry. A fresh undispatched line should retain truthful no-dispatch state and be safely removable or explicitly resumable.

Preparation may already have saved and authorized a draft. Do not delete that draft or treat authorization as a charge. Do not apply a local cancellation shortcut once dispatch may have occurred; that path still requires authoritative reconciliation and must preserve a capture that wins the race.
