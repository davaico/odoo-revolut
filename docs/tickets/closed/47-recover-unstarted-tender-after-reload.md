## Investigation boundaries

`restorePaymentLine` treats persisted waiting as potentially started;
`cancelPayment` maps an empty lookup to interrupted/false; repeated identical
messages are suppressed. These code paths reproduce the observed symptoms.
Unknown legacy waiting lines are deliberately protected by existing tests.
An empty lookup alone must not be reinterpreted as permission to delete,
resume or release possible financial exposure. Establish a durable, server-owned
proof of an unstarted preparation failure or another safe recovery contract.

**Current behavior:** The native draft can retain a waiting Revolut tender

local no-start evidence. Delete then performs an empty lookup and leaves the
tender locked; Resume is absent and repeated clicks can appear inert.

**Desired behavior and recovery contract:**

- A bounded explicit recovery action asks the server to classify the exact
  persisted draft sale and tender. Reload and status recovery can restore
  available actions but cannot start a charge. Keep the original order and,
  for Resume, the original tender UUID and native identity.
- Validate caller access, company, register, original open session, unique
  order/tender ownership, method, currency and amount against canonical server
  records. Browser flags, error text, waiting status or `False` discovery are
  insufficient proof. Inspect complete relevant operation history, references,
  reservations and dispatch evidence under the existing financial/native locks.
- Establish a durable server-owned recovery disposition or admission revision
  before exposing safe actions. Recovery must invalidate every outstanding
  start authorization for that tender, including a preparation response that
  arrives later. A one-time unlocked absence check or browser-only flag is
  insufficient. Native removal and subsequent start admission must recheck
  current authority under the same serialization boundary.
- If start wins the race, recover its existing operation and retain exposure
  guards. If recovery wins, a delayed old start must be rejected without
  dispatch. An explicit Resume obtains current cart authorization and tender
  admission before starting exactly once; Price Control and manager approval
  still apply. Safe removal durably retires the old tender admission so stale
  requests cannot charge after another tender settles the sale.
- Support the preserved existing fixture, which has no prior durable failure
  marker. A guarded server classification may establish current no-start
  authority from complete retained history and fencing; merely adding a marker
  for future failures does not satisfy this ticket. Missing, ambiguous or
  inconsistent history/ownership fails closed. Unknown legacy waiting lines
  without that complete authority, surviving references, pending exposure and
  verified payments keep their existing protections.
- Show actionable preparation/recovery feedback. Repeated explicit actions
  must show understandable current feedback or visible recovery progress;
  failed/offline recovery never silently unlocks money or strands native busy
  state. Recovery and removal issue no Merchant requests.

- `RevolutPaymentState`, `restorePaymentLine`, `paymentActions`, `screenCancel`

- `ReturnAllocation.acquire_native_mutation`, operation order locking,
