## Agent Brief

**Category:** bug

**Summary:** Make removal of a saved, safely cancelled Revolut sale tender
survive native Odoo 19 draft reload without restoring an unintended row.

**Current behavior:**
Source assessment of Odoo 19 finds that ordinary cancelled-tender removal
uses native local deletion whose pending commands do not survive IndexedDB
reload. Server recovery returns retained operation history even when removal
is explicitly requested. Cart reconstruction does not retain recovered-tender
history after the last native Revolut tender disappears. Odoo 18 reproduced
restoration of the original cancelled tender alongside a new unsent allocation;
an equivalent Odoo 19 browser reproduction is still required.

**Desired behavior:**
Hide a saved sale tender only after durable, idempotent server retirement
confirms removal is safe. Refresh must preserve each legitimate pending
allocation exactly once and retain original operation and dispatch history.
Uncertain or verified tenders stay protected. Recovery never starts collection.
Offline or lost retirement replies retain recoverable original identities.
Editable local amounts, including zero, must not redefine saved tender identity.

**Key interfaces:**
- Native `PaymentScreen.deletePaymentLine()` and `PosOrder.removePaymentline()`:
  coordinate durable saved-tender removal and acknowledge only its completed
  Odoo 19 deletion command without losing unrelated pending edits.
- `RevolutPaymentState.removeRecoveredPayment()`: retain guarded recovery,
  drain the cancelled foreground request and reject stale or mismatched proof.
- `revolut_remove_unstarted_payment()` and checkout-state recovery: enforce
  server-owned ownership, saved amount, retained history and retirement fences.
- Native cart-delta reconstruction: preserve existing cart contents after the
  final Revolut tender is retired.

**Acceptance criteria:**
- [x] Demonstrate a failing Odoo 19 native browser regression before correction:
      start/cancel, remove, create an unsent allocation, edit zero/back and reload.
      Record UUIDs, saved identities and visible/model membership; minimise it.
- [x] Repeated refresh restores the pending allocation once without restoring
      the retired tender or creating financial dispatch or capture.
- [x] Retirement is idempotent for server-proven retry-safe history, preserves
      all operation/dispatch history and blocks uncertain/verified removal.
- [x] Canonical saved amounts survive local zero/back edits; saved zero-value
      unstarted tenders may be removed but cannot start collection.
- [x] Offline/lost replies preserve recovery, and delayed cancelled foreground
      results cannot publish onto the removed tender.
- [x] Native cart edits survive retirement of the final Revolut tender; existing
      saved-unstarted recovery, cancellation, distinct tenders and split checkout
