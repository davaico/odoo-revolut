## Triage findings

`ReturnAllocation._return_components` computes each return's fraction of an original line and rounds it independently to currency minor units. Quantity usage and monetary reservations are checked separately. No per-return allocation conserves the line's remaining cents across those independently rounded fractions. The native return target also derives from this calculation, so merely capping the selected payment at the remaining provider balance cannot resolve checkout.

### Reproduction and evidence

Use a two-decimal currency, an untaxed original quantity 1, a frozen base amount of 1,234 minor units and one Revolut tender. Return quantity 0.25, followed by the remaining 0.75:

| Step | Current computed target | Source balance before refund |
| --- | --- | --- |
| First quarter | 309 minor units | 1,234 |
| Remaining three quarters | 926 minor units | 925 |

The production methods produce `[(309, 0), (926, 0)]` for base/tip components, demanding 1,235 minor units. Source/component caps correctly refuse the over-refund. Allocating 925 cannot finalize the independently computed 926 return because settlement requires exact tender equality. Original price/discount changes are rejected; an all-Revolut sale has no original cash tender to absorb the difference.

The reviewer and lead auditor independently executed the production `_return_components` and `normalize_amount` bodies with fake ORM record containers. This confirms the arithmetic. Reservation and settlement consequences were traced statically, **not reproduced end-to-end in Odoo**. The existing `test_repeated_partial_refunds_can_use_full_remaining_balance` uses two exactly divisible halves of 1,234, so it misses this case. Ticket 09 requires repeated partial/remaining-balance refunds; ticket 24 explicitly retains fractional quantities. This is an approved-flow defect.

### Proposed fix direction and unresolved engineering choices

Use cumulative monetary entitlement and an authoritative frozen return allocation, rather than independently rounding each fraction. One candidate is rounded cumulative entitlement for consumed quantity minus already allocated entitlement; the final eligible quantity receives the remaining amount. This is a candidate algorithm, not a sufficient implementation specification: reservation releases, multiple tenders, and historical evidence must also be handled.

For the example, the first accepted return remains 309 and the final accepted return becomes 925. Reservation must establish the target under the original-sale lock before financial dispatch; discovery can only offer a provisional amount. Multiple payment allocations on one return consume its quantities and target once. Pending and uncertain operations retain their claims. Releasing a definitively failed reservation must not recalculate another return that already dispatched.

The native representation of the one-cent difference is not yet proven. Investigate the smallest pinned-Odoo-compatible way for the saved return, displayed total, receipt, tax/accounting output and payment amounts to agree. An authoritative total override alone is not evidence that accounting balances correctly. Do not silently change product prices, invent an ordinary product, raise provider caps, or add a blanket settlement tolerance.

Historical refunds require a separate compatibility check. Preserve completed amounts/references and existing uncertain snapshots. Use trustworthy historical allocations where sufficient; older multi-line or mixed-tender records may lack enough per-line evidence. Do not fabricate that history. Record a conservative recovery path when exact residual entitlement cannot be established. External refunds retain their existing unknown-product/base/tip guards.

## Agent Brief

**Category:** bug

**Summary:** Make successive partial returns conserve the original refundable amount while keeping native documents and provider allocations consistent.

**Current behavior:** Individually rounded fractions can require more money than was originally paid, leaving the final eligible return impossible to settle.

**Desired behavior:** Supported returns of all eligible original quantity can consume exactly the remaining original entitlement without exceeding any source, base/tip or tender cap. Once accepted for dispatch, a return's target is durable and stable through retries and recovery.

**Key interfaces:** `ReturnAllocation` source discovery/reservation/settlement, `_revolut_return_target_minor`, saved native return persistence, refund operation component evidence, and native receipt/accounting projection. No new provider capability is required.

**Implementation milestones:** First establish a failing public-RPC/native-finalization regression. Finally implement durable allocation and verify concurrency, recovery and historical compatibility. The cumulative formula above is a candidate, not a prescribed design. Do not claim completion from a helper-only fix.
